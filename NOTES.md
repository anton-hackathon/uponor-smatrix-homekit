# Uponor × HomeSpan — рабочее состояние и заметки

Состояние на 2026-08-05. **Всё работает и проверено на живой системе.** Плата на
постоянном питании, у контроллера X-245, сопряжена с iPhone. Ниже — что закрыто и
подводные камни, о которых стоит помнить при будущих правках.

## Что работает (подтверждено)

| Слой | Чем подтверждено |
|---|---|
| Сборка | `pio run` чисто, ~70 % флеша, ~19 % RAM |
| Wi-Fi | `<адрес платы>`, `uponor.local`, задержка 7–90 мс, 0 % потерь |
| Шина RS485 | `bus rx` растёт, `packets` растёт, `discarded` ~0.2 %, `timeMaster=yes` |
| HomeKit-сопряжение | мост + 5 термостатов, база HAP без ошибок |
| Чтение | температура/уставка/влажность/режим — живые, разные по комнатам |
| Запись уставки | `[uponor] 0x… setpoint -> N C`, значение доходит до термостата |
| Ручная смена на пульте | приходит в «Дом» (проверено 17.5 → 24.5) |
| Веб-лог | `http://uponor.local/status` — счётчики шины и состояние зон |
| OTA | `pio run -e ota -t upload`, стабильно после исправления энергосбережения |

## Решённые симптомы «Дома» (история, чтобы не повторять)

1. **Влажность не видна на плитке.** Причина не в коде: «Дом» вообще не рисует
   значение датчика климата на плитке — только в климатической сводке вверху
   экрана. Решение: датчик влажности вложен вторым сервисом `HumiditySensor`
   внутрь аксессуара-термостата (плитки не создаёт, питает сводку). Отдельными
   аксессуарами влажность делать НЕ надо — это 5 лишних плиток без значения.
   Для покомнатных значений (не общий диапазон) — разложить аксессуары по
   комнатам в самом «Доме», без перепрошивки.

2. **Панель термостата не открывалась.** Причина: `setValidValues([HEAT,COOL])`
   урезал набор режимов без `OFF`, и «Дом» отказывался рисовать панель. Решение:
   набор режимов НЕ ограничивать (как в эталонном термостате HomeSpan). Диапазоны
   при этом обязаны укладываться в спеку HAP: `TargetTemperature` 10..38,
   `CurrentTemperature` 0..100 — иначе панель тоже может не открыться.

3. **Переключатель режима «не работал».** Режим задаёт X-245 на всю систему, в
   шину не пишется. Совсем убрать переключатель нельзя — режим обязателен для
   термостата HAP. Решение: `TargetHeatingCoolingState->removePerms(PW)` —
   характеристика read-only, «Дом» не шлёт смену, кнопки видны но неактивны и
   лишь отражают фактический режим. Синхронизация — в `onDeviceData` (case
   `UPONOR_ID_DEMAND`), не в `loop()`.

## Возможная будущая доработка — затирание своей же записи

Защиты «pending write» нет: после записи из «Дома» первый же пакет с шины
вызывает `publishTargetTemperature_()` и перепишет значение тем, что сообщил
контроллер. Пока на живой системе проблем не давало (X-245 применяет уставку
быстро), но если ползунок в «Доме» начнёт «отскакивать» — смотреть сюда.

Связано с расписанием (исследование 2026-08-05): у программируемых термостатов есть
недельная программа comfort/eco. Она хранится В термостате, по шине НЕ
транслируется (только текущие значения). Наша запись уставки работает как
временное ручное переопределение и держится до следующего перехода расписания — потом
расписание применяет своё. Это штатно, не баг; отражение в «Доме» корректное
(читаем 0x3B + ECO из 0x3E). Программировать расписание из HomeKit нельзя. Всё
это описано в FAQ README. Наблюдать переходы расписания — включить DUMP_ENABLED
на сутки и отслеживать смену 0x3E и скачки 0x3B.

## Питание — РЕШЕНО (заметка о том, что было)

Было: от USB-C MacBook плата работает, от USB-C блока питания в розетку тем же
кабелем — не стартует, светодиоды не зажигаются.

**Причина — согласование питания USB-C, а не поломка платы.** USB-C источник не
подаёт 5 В без запроса: зарядник смотрит на линии CC и ждёт, что потребитель
подтянет их к земле резисторами 5.1 кОм (Rd). Для кабеля USB-C → micro-USB эту
роль играет резистор 56 кОм внутри кабеля. На дешёвых платах Rd часто не распаяны,
в дешёвых кабелях 56 кОм не заложены — зарядник видит «ничего не подключено» и
держит 0 В. Порт MacBook при этом не чистый PD: он держит дежурные 5 В для
неопознанных устаревших устройств, поэтому от него всё поднимается.

Варианты по убыванию надёжности:

1. **Зарядник с обычным USB-A разъёмом** + кабель USB-A → (разъём платы). На USB-A
   5 В присутствуют всегда, согласования нет вообще. Лечит обе возможные причины
   сразу. Ток: Wi-Fi-пики у ESP32 до ~500 мА, зарядник от 1 А берётся с запасом.
2. **5 В на пин VIN**, минуя USB целиком — встроенный регулятор даст 3.3 В.
3. USB-C зарядник с заявленной поддержкой устаревшего режима 5 В либо другой кабель — лотерея,
   первые два варианта предпочтительнее.
4. Питание от самого X-245 — в README не описано, есть ли там подходящая клемма.
   Проверять по документации контроллера, не действовать наугад.

Модуль RS485 (DollaTek) берёт 3.0–30 В и питается от **3.3 V** платы, как сейчас
и распаяно — отдельного источника ему не нужно.

**Важно при любом варианте:** если плата и X-245 питаются от разных источников,
нужен провод с GND модуля на земляную клемму X-245. Без общей опоры приёмнику
нечем сравнивать A и B, и это даёт ровно ту картину, что сейчас — `rx=0`.
Это первый подозреваемый, когда питание будет решено.

## Исследование шины 2026-08-05 — что реально ходит по шине

Снят полный дамп всех регистров всех адресов (режим `DUMP_ENABLED` в
[src/main.cpp](src/main.cpp), сейчас выключен — включить и загрузить заново по OTA,
если снова понадобится). Итог: **нового полезного нет.**

- **Наружная температура `0x2D` = `7FFF`** у всех — датчик к контроллеру не
  подключён. Вывести уличную температуру в «Дом» нечего.
- **Напольные датчики `0x41`** не шлются вовсе.
- **ECO/расписание `0x3E` = `0000`** — сейчас неактивны (значение появится,
  когда включится эконом-режим или программа Uponor).
- Всё ценное (`0x40` темп, `0x3B` уставка, `0x42` влажность, `0x3D` режим/актив,
  `0x37/0x38` границы, `0x3C` ECO-откат) уже отображается.

**Санузлы исключены из охлаждения — подтверждено дампом**, не гипотеза:

| Регистр | Рабочие | Санузлы |
|---|---|---|
| `0x3F` mode2 | `1C03` | `1803` (бит `0x0400` «cooling allowed» сброшен) |
| `0x35` | `8000` | `0000` |

Расшифровка битов `0x3F` подтверждена анализом kroimon
(github.com/kroimon/uponor-smatrix-analysis): `0x0400` = разрешено охлаждение,
`0x0800` = разрешён нагрев. У санузлов `1803` = нагрев разрешён (`0x0800` стоит),
охлаждение запрещено (`0x0400` сброшен). Отсюда прогноз про HEAT — не догадка, а
следствие битов.

Бит активности `0x0040` в `0x3D`: у рабочих поднимается при охлаждении, у
санузлов не поднимается никогда (в режиме COOL). Запись уставки по шине в санузлы
при этом ПРОХОДИТ (проверено: Bathroom1 принял 22.0 и держал) — блокировка только на
физическом пульте. Санузлы заработают при переключении всей системы в HEAT.

Режим heat/cool — общесистемный, бит `0x1000` в `0x3D` у всех зон (сейчас COOL).
Единственный осмысленный «квартирный» параметр, если захочется индикатор.

## ⚠️ ECO-откат применяется неверно в режиме охлаждения (латентный баг)

**Найдено в мануале 2026-08-06**, меню `03 ECO mode setback temperature`
(значение по умолчанию 4 °C, диапазон 0–11):

> The setting adjusts the current setpoint with the set value. **In heating mode
> the setpoint is reduced, and in cooling mode it is increased.**

Наш код в `uponor_zone.cpp` **всегда вычитает** откат:

```cpp
uint16_t raw = eco_active_ ? (target_temp_raw_ - eco_setback_raw_) : target_temp_raw_;
// и обратно в update(): raw += eco_setback_raw_;
```

В режиме COOL надо **прибавлять** при чтении и вычитать при записи — знак
инвертируется. Регистр `0x3C` = `0x0048` = 7.2 °F = ровно 4.0 K, что совпадает с
документированным значением по умолчанию 4 °C — значит регистр опознан верно, ошибка только в знаке.

**Сейчас не проявляется:** ECO не активен (`0x3E = 0000` у всех зон, программа
`00 Program` по умолчанию Off). Проявится, когда включат расписание или Forced ECO.

Правило из мануала однозначное, так что править можно без гадания — но проверить
сейчас нельзя (ECO выключен). Логично исправить вместе с offset, когда появятся
heating/ECO-данные. Та же природа ошибки, что у offset: правило зависит от режима,
а мы применяем односторонне.

## Сдвиг +2 °C — разгадан, но ⚠️ зимой сломается

**Причина найдена** (документация Uponor, 2026-08-05): это штатный параметр
«Heating/cooling offset», значение по умолчанию 2 °C. При переключении в ОХЛАЖДЕНИЕ уставка
увеличивается на offset → экран термостата = `0x3B` + 2 (в `0x3B` базовая
уставка, на экране эффективная). Снимает обе прежние загадки: почему ровно 2.00
в °C на Фаренгейтовой шине (offset — отдельный параметр в °C) и почему граница
`0x38` не сдвинута (offset к setpoint, не к границам).

**⚠️ Риск зимы:** документация — «when switching back to heating, the value is
used to REDUCE the setpoint», то есть в HEAT offset меняет знак. Наш код
(`UPONOR_TARGET_TEMP_OFFSET`) прибавляет ЖЁСТКО, независимо от режима. Проверено
только в COOL. Зимой `+2` почти наверняка неверен — ошибка до 4 °C. Код НЕ трогать
вслепую (лето работает). Сначала факты: (1) проверить параметр offset в приложении
Uponor Smatrix Pulse / меню контроллера — если настраивается, можно обнулить в
системе и убрать нашу поправку совсем; (2) снять heating-данные при переключении
(дамп + сравнить экран с `0x3B`) и сделать offset режим-зависимым.

## Если шина замолчит (`rx=0`)

Порядок проверки железа: питание модуля → полярность A/B (перепутать безопасно) →
общая земля с X-245 → TXD модуля на GPIO16. Индикатор RXD на модуле должен мигать
сам по себе. Лог со сбросом: `./capture.sh 30` или веб-лог `/status`. Если плата
и X-245 питаются от разных источников — обязателен провод с GND модуля на землю
X-245, без общей опоры приёмнику нечем сравнивать A и B.

## Причина задержек и потерь — энергосбережение Wi-Fi

**Найдено 2026-08-04.** На классическом ESP32 arduino-esp32 по умолчанию включает
`WIFI_PS_MIN_MODEM`, а HomeSpan этого не меняет:

```cpp
// framework-arduinoespressif32/libraries/WiFi/src/WiFiGeneric.cpp:386
#if CONFIG_IDF_TARGET_ESP32S2
wifi_ps_type_t WiFiGenericClass::_sleepEnabled = WIFI_PS_NONE;
#else
wifi_ps_type_t WiFiGenericClass::_sleepEnabled = WIFI_PS_MIN_MODEM;   // ← наш чип
#endif
```

Плата спит между маячками точки доступа и просыпается только в свои окна.
Входящие пакеты копятся на роутере и приходят пачками — отсюда наблюдаемая
картина: задержка от 27 до 670 мс с огромным джиттером при почти нулевых
потерях, и срывы OTA по таймауту под нагрузкой.

Это снимает подозрение с радио: **RSSI −51 дБм — нормальный уровень** (проблемы
начинаются после −70), и потому перенос платы к самому роутеру ничего не изменил.
Дело было в настройке, а не в сигнале.

**Правка внесена** в [src/main.cpp](src/main.cpp) — `WiFi.setSleep(false)` в ветке
подтверждения прошивки, то есть после того как Wi-Fi поднялся (`esp_wifi_set_ps()`
требует уже инициализированного Wi-Fi). Расход тока вырастает примерно на 30 мА,
для платы с постоянным питанием несущественно.

**Но загрузить эту правку по воздуху не удалось** — OTA срывается именно из-за той
проблемы, которую она лечит. Нужна одна загрузка по USB, после чего OTA должна
стать надёжной.

## Полезные команды

Загрузка прошивки (только 115200, CH340 разрывает связь на 460800):

```bash
source .venv/bin/activate && pio run -t upload
```

Лог со сбросом платы (без сброса порт молчит):

```bash
./capture.sh 30
```

Стереть сопряжение HomeKit, если «Дом» снова скажет «No se puede añadir el accesorio» —
это значит, что на плате застряло незавершённое сопряжение (`Paired Controller` в логе есть, а на
телефоне сопряжения нет; HomeSpan тогда обязан отвечать `Error=Unavailable`). Команда `U`
в Serial стирает контроллеров, не трогая Wi-Fi:

```bash
source .venv/bin/activate && python -c "
import serial,time
p=serial.Serial(); p.port='/dev/cu.usbserial-XXXX'; p.baudrate=115200; p.timeout=0.3
p.dtr=p.rts=False; p.open(); time.sleep(0.5)
p.write(b'U\r\n'); p.flush(); time.sleep(3)
print(p.read(4096).decode('utf-8','replace')); p.close()"
```

Проверка со стороны сети:

```bash
ping -c 5 uponor.local && dns-sd -t 6 -L "Uponor Smatrix" _hap._tcp
```

В TXT-записи `sf=1` — не сопряжён и готов к сопряжению, `sf=0` — уже сопряжён.

Загрузка по воздуху (OTA):

```bash
source .venv/bin/activate && pio run -e ota -t upload
```

## Что пробовали и отвергли

- **Индикатор режима зима/лето на уровне квартиры** через `Service::ContactSensor`
  (отдельный аксессуар, читал `0x1000` из `0x3D`). Собрали, показали, откатили:
  «Дом» рисует контакт-сенсор как «Abierto/Cerrado», семантика для режима чужая.
  Честного способа показать «Лето/Зима» словами в HomeKit нет; режим и так виден
  в каждой комнате. Если снова захочется — только виртуальный термостат «Sistema»
  read-only, но это лишняя плитка-термостат. Код индикатора удалён из репозитория.
